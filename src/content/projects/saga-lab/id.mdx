## Tentang project

Project belajar untuk saga pattern. Satu checkout dipecah ke tiga service, yaitu Order, Inventory, dan Payment, yang masing-masing punya database sendiri, sehingga satu transaksi database tidak bisa menjaga semuanya tetap konsisten. Saga yang mengambil alih tugas itu: setiap service menjalankan transaksi lokalnya sendiri, dan kalau langkah berikutnya gagal, langkah sebelumnya dibatalkan dengan compensating action.

Project ini berjalan di lokal dan tidak di-deploy.

## Teknologi

- **Backend:** tiga aplikasi Laravel 11 (Order, Inventory, Payment), masing-masing dengan database SQLite sendiri
- **Komunikasi:** Laravel job di Redis queue, satu queue per service
- **Frontend:** Next.js dengan TanStack Query

Kalau pembayaran berhasil, Order menandai order sebagai `confirmed`. Kalau stok tidak cukup, Inventory mengirim `stock-unavailable` dan order langsung gagal sebelum sampai ke Payment. Payment tiruan ini sengaja menolak setiap quantity genap, supaya alur gagal bisa diuji kapan saja.

- Service hanya berkomunikasi lewat queue, tidak pernah lewat HTTP, dan tidak ada koordinator pusat (choreography).
- Setiap reservasi disimpan sebagai baris tersendiri, jadi saat release Inventory tahu persis berapa stok yang harus dikembalikan.
- Stok dicek dan dikurangi dalam satu update bersyarat, jadi dua order tidak bisa sama-sama mengambil stok terakhir.
- Event baru dikirim setelah transaksi lokal ter-commit, dan setiap handler aman dijalankan dua kali.
- Frontend menampilkan order sebagai "sedang diproses" dan mengecek statusnya secara berkala sampai `confirmed` atau `failed`, lengkap dengan timeline setiap perubahan status.
